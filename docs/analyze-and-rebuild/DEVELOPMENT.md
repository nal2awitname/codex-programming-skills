# พัฒนา analyze-and-rebuild ต่อ

รุ่น 2.0 มีโค้ดเครื่องมือและชุดทดสอบที่รันได้ ดู [ส่วนประกอบและคำสั่ง](V2_TH.md) และ [operator guide](../../skills/analyze-and-rebuild/references/toolkit-guide.md)

## เริ่มแก้ไข

```bash
git clone https://github.com/nal2awitname/codex-programming-skills.git
cd codex-programming-skills
git switch -c improve/analyze-and-rebuild
```

ดูตำแหน่งส่วนประกอบใน [คู่มือ](README_TH.md) เก็บคำสั่งหลักไว้ใน `skills/analyze-and-rebuild/SKILL.md` และรายละเอียดเฉพาะงานไว้ใน `references/` โดยเชื่อมจากคำสั่งหลัก คู่มือสำหรับผู้พัฒนาและแม่แบบโครงการอยู่ภายนอกโฟลเดอร์สกิล

## เลือกจุดที่จะแก้

| สิ่งที่ต้องการเพิ่ม | แก้ส่วนใด | ตรวจรับอย่างไร |
| --- | --- | --- |
| ภาษา/แพลตฟอร์มใหม่ | `references/analysis-guide.md` | ระบุภาษาจากหลักฐานหลายด้าน และแยก static จาก runtime |
| พฤติกรรมหรือ interface แบบใหม่ | `references/behavior-spec.md` | มี input/output, error, state และกรณีขอบเขตเพียงพอให้เขียนเอง |
| วิธีทดสอบเพิ่ม | `references/verification.md` | บันทึกผลรันจริง ไม่ปรับ expected result เพื่อซ่อนข้อผิดพลาด |
| รูปแบบโครงการหรือการส่ง GitHub | `references/github-handoff.md` | เก็บโค้ดใหม่ครบ รักษาไฟล์เดิม และอ่านผลจากปลายทางกลับมาตรวจ |
| ชื่อหรือคำสั่งเริ่มต้น | `agents/openai.yaml` | ข้อความตรงกับสกิลและยังเรียก `$analyze-and-rebuild` ได้ |

## ตรวจรับการแก้ไข

1. ตรวจ YAML frontmatter ให้มี `name` และ `description` ที่ถูกต้อง และตรวจลิงก์อ้างอิงทั้งหมด
2. ตรวจว่าข้อห้ามคัดลอก แปลทีละบรรทัด เปลี่ยนชื่ออำพราง และส่ง source-derived pseudocode ยังอยู่ครบ
3. ทดลองคำขอ “วิเคราะห์อย่างเดียว” ให้ได้รายงานที่อ้างหลักฐาน โดยไม่เริ่มสร้างโปรแกรมเกินขอบเขต
4. ทดลองสร้างใหม่จากโปรแกรมสังเคราะห์ขนาดเล็ก แยกบริบทผู้วิเคราะห์และผู้เขียนใหม่ ส่งให้ผู้เขียนเฉพาะข้อกำหนดและข้อมูลสังเคราะห์
5. ใช้กรณีปกติ ขอบเขต ข้อมูลผิด และการเปลี่ยนสถานะที่เกี่ยวข้อง บันทึกคำสั่งและผลรันจริง
6. หากไม่มี runtime หรือเข้าไม่ถึงบริการ ให้ตรวจว่ารายงานบอกส่วนที่ยังยืนยันไม่ได้
7. สำหรับการส่ง GitHub ตรวจรายการไฟล์และ head ก่อนเขียน แล้วอ่าน commit/tree กลับมาตรวจว่าเพิ่มเฉพาะสิ่งที่ตั้งใจและรักษาไฟล์เดิม

การแยกบทสนทนาโดยใช้ filesystem ร่วมกันเป็นการแยกบริบท ไม่ใช่การปิดกั้นการเข้าถึงต้นฉบับ บันทึกวิธีที่ใช้จริงและไม่อ้างผลจากคะแนนความเหมือนเพียงอย่างเดียว

## บันทึกการเปลี่ยนแปลง

เขียนคำอธิบาย commit หรือ pull request ว่าแก้พฤติกรรมใด เหตุใด และทดสอบอย่างไร หากเปลี่ยนขอบเขตหรือวิธีส่งงาน ให้อัปเดตคู่มือและแม่แบบที่เกี่ยวข้องด้วย หลีกเลี่ยงการเพิ่มไฟล์ตัวอย่างหรือ dependency ที่ไม่ได้ใช้

## นำเวอร์ชันใหม่ไปใช้

สำเนาใน GitHub กับสกิลส่วนตัวที่ติดตั้งไว้เป็นคนละสำเนา การแก้ใน GitHub ไม่อัปเดตตัวที่ติดตั้งให้อัตโนมัติ หลังแก้ไขให้สั่งอัปเดตสกิลจาก repository และ path ที่ระบุ เช่น:

```text
Update analyze-and-rebuild from nal2awitname/codex-programming-skills
at path skills/analyze-and-rebuild; verify and record the installed version.
```

เมื่อต้องการแก้เฉพาะสกิลที่ติดตั้ง ให้ระบุด้วยว่าต้องการบันทึกกลับ GitHub เพื่อให้ทั้งสองสำเนาตรงกัน
